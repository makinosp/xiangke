## Context

See proposal.md - Why. The `.tres` resources are the runtime source of truth for
game data, but the authoritative schema and validation rules live in Rust core
(`extensions/core/src/character.rs`, `validator.rs`), which never reads the real
files. Four hand-maintained schema copies exist today: GDScript resource
classes, the Go roster tool's regex parser, Rust serde structs, and hand-written
JSON in `extensions/core/tests/integration.rs`.

Relevant constraints discovered in the codebase:

- `systems/data/data_validator.gd` is marked `@deprecated` in favor of the Rust
  validator — the GDScript validator is not authoritative.
- GDScript `-s` script mode hangs with the GDExtension (documented in test
  memory); tool scripts must run as **scenes** (`res://*.tscn`) under
  `godot --headless`.
- `DataLoader` (`systems/data/data_loader.gd`) already discovers and loads all
  `.tres` files, but silently substitutes stat-1 "Unknown" placeholders for
  missing or corrupted files.
- The core validator exposes `validate_move(&MoveData)`,
  `validate_character(
  &CharacterData, &all_moves)` and a `ValidationResult`
  collector with `add_error` / `add_warning` / `is_valid` / `get_summary`.
- The export output is temporary by decision (no committed snapshots).

## Goals / Non-Goals

**Goals:**

- One command, `just verify-data`, that catches `.tres` ↔ core schema drift and
  rule violations at development time.
- Reuse the game's own load path (DataLoader) and the core's own serde structs
  and validator — introduce no third parser and no fourth schema copy.
- Clear, non-zero exit codes so the command can be scripted later.

**Non-Goals:**

- Roster/display reporting — the Go tool stays as-is for now.
- Committing export snapshots for CI diff detection.
- Replacing runtime GDScript data loading.
- Validating the type chart (it lives in `scripts/type_chart.gd`, not `.tres`).
- Web/WASM support for the checker.

## Decisions

### D1: Godot export scene writes temporary JSON

`tools/data_export.tscn` + `tools/data_export.gd` (a tool scene) runs under
`godot --headless`, loads everything through `DataLoader.load_all()`, serializes
each `CharacterData` / `MoveData` to a dictionary (explicit field enumeration in
GDScript — `to_json()` cannot serialize custom Resources), writes the JSON to a
path taken from `--export-path=<abs>` via `OS.get_cmdline_user_args()`, then
quits with code 0 on success / 1 on failure.

- **Why scene mode, not `-s`**: GDExtension hangs in `-s` script mode; the
  existing test runner already uses the scene convention.
- **Why DataLoader**: reuses the runtime discovery (including DLC dirs),
  avoiding a third file-discovery implementation.
- **Alternative rejected**: a standalone GDScript that re-implements discovery —
  would duplicate the schema and logic again.

### D2: Rust binary crate `tools/xiangke_checker` as a workspace member

A new binary crate in the Cargo workspace depending on `xiangke-core` and
`serde_json`. It reads the export JSON, deserializes into the core
`CharacterData` / `MoveData` structs, runs `validate_move` /
`validate_character` per entity into a single `ValidationResult`, prints the
summary, and exits non-zero when `!is_valid()`.

- **Why Rust**: schema and rules are then defined once, in core; the checker is
  a thin CLI over the authoritative code.
- **Strict field check**: deserialize to `serde_json::Value` first and compare
  keys against the expected field sets, so renamed/added/removed fields are
  reported. Serde's default behavior silently ignores unknown fields, which
  would miss that class of drift. This strictness lives in the checker crate
  only — the core structs keep `deny_unknown_fields` off so runtime behavior is
  unchanged.
- **Alternatives rejected**: extend `xiangke-godot-bridge` (runtime concern, not
  a dev tool); a Go binary (adds a duplicate schema).

### D3: Integration test fixture becomes generated output

Replace the hand-written inline JSON in `extensions/core/tests/integration.rs`
with a committed fixture at `extensions/core/tests/fixtures/resources.json`,
regenerated by `just verify-data --update-fixture`. `cargo test` stays
self-contained, and the fixture is generated rather than hand-maintained,
killing the fourth schema copy.

- **Tradeoff**: the committed fixture can go stale — live validation always uses
  the temp export, and `--update-fixture` regenerates it.

### D4: justfile recipe as the single entry point

- `just verify-data`: export to a temp path → run checker → report.
- `just verify-data --update-fixture`: additionally regenerate the committed
  integration fixture from the same export output.

## Risks / Trade-offs

- [Silent placeholder substitution] `DataLoader` swaps missing/corrupted files
  for "Unknown" stat-1 placeholders; the export would otherwise succeed with
  bogus data → the export scene flags any placeholder (name "Unknown" and/or
  "Data missing or corrupted" description) as an error. A real character
  legitimately named "Unknown" would false-positive — unlikely, and the
  description check narrows it.
- [Fixture staleness] The committed integration fixture can drift from live
  resources → mitigated by D3/D4: live verification always uses the temp export,
  and regeneration is one command.
- [Godot required for verification] `verify-data` needs a local Godot install —
  acceptable for a dev-only tool; CI is out of scope.
- [Field list duplicated in export scene] The export scene must enumerate
  resource properties in GDScript; a new property added to the resource classes
  needs the export scene updated → the checker's strict key check and the
  fixture test surface the resulting mismatch at verify time.
- [GDScript JSON has no typed enum guarantees] Type fields are exported as raw
  integers; the checker deserializes them into the core enums, so out-of-range
  values surface as deserialization errors.

## Migration Plan

Purely additive dev tooling. No runtime code changes, no rollback concerns.
`just verify-data` is new; all existing commands behave as before.

## Open Questions

None blocking. Whether to eventually wire `verify-data` into CI is deferrable
without changing the specs or approach.
