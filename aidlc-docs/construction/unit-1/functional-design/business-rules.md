# Business Rules — Unit 1: Resources (Shared Data)

## Overview

Business rules and validation constraints for the shared data layer. These
ensure data integrity and consistent behavior across all systems.

---

## Character Data Rules

### CR-1: Character Identity

- Each character MUST have a unique `id` (lowercase snake_case, e.g.,
  "zhuge_liang").
- Each character MUST have a non-empty `name` (1–20 characters, Japanese
  kanji/kana).
- Character `id` MUST NOT change after creation (used as lookup key).

### CR-2: Character Stats

- All stats (hp, attack, defense, speed) MUST be integers in range [1, 999].
- Stats are unique per character (no shared templates).
- The sum of all four base stats MUST NOT exceed 2000 (balance constraint).
- No single stat MAY exceed 500 (prevent extreme specialization).

### CR-3: Character Type Assignment

- Each character MUST have exactly one primary type.
- Primary type MUST be one of the 7 valid types: Wood, Fire, Earth, Metal,
  Water, Yang, Yin.
- A character MAY have an optional secondary type.
- If a secondary type is set, it MUST differ from the primary type.
- A character's primary and secondary types determine their defensive type
  effectiveness (see Dual-Type calculation in business-logic-model.md).
- Approximately 30–50% of the roster SHOULD have a secondary type for balanced
  variety.

### CR-4: Character Move Assignment

- Each character MUST have exactly 4 moves.
- All 4 moves MUST reference valid move IDs that exist in the move data.
- A character's moves MUST include at least one move with `power > 0`.
- Move types MUST be one of the 7 valid types (no type restrictions per
  character).

## Move Data Rules

### MR-1: Move Identity

- Each move MUST have a unique `id` (lowercase snake_case, e.g., "fire_strike").
- Each move MUST have a non-empty `name` (1–20 characters).
- Move `id` MUST NOT change after creation.

### MR-2: Move Power and Accuracy

- `power` MUST be an integer in range [0, 255].
- `accuracy` MUST be an integer in range [1, 100] (moves always have a chance to
  hit).
- If `power` is 0, the move is non-damaging (status/heal only).
- If `power` > 0, at least one of `effect`, `statMod`, `hitCount`, `recoil`, or
  `healing` SHOULD be defined (moves should have purpose).

### MR-3: Move Effect

- `effect` MUST be one of: None, Burn, Poison, Confusion, Chain, Charm.
- `effectChance` MUST be an integer in range [0, 100].
- If `effect` is None, `effectChance` MUST be 0.
- If `effect` is not None, `effectChance` MUST be in range [1, 100].

### MR-4: Move Stat Modification

- If `statMod` is defined, it MUST include a valid `stat` (Attack, Defense,
  Speed).
- `statMod.stage` MUST be an integer in range [-3, +3] per move application.
- Multiple stat modifications from moves are cumulative but clamped to [-6, +6].

### MR-5: Move Multi-Hit

- `hitCount` MUST be an integer in range [1, 5].
- If `hitCount` is 1, the move is a single-hit move.
- If `hitCount` > 1, each hit uses the same `power` and `type`.

### MR-6: Move Recoil

- `recoil` MUST be an integer in range [0, 100] (percentage of damage dealt).
- If `recoil` > 0, the move MUST have `power > 0` (recoil requires damage).
- Recoil damage is calculated after all hits of a multi-hit move.

### MR-7: Move Healing

- `healing` MUST be an integer in range [0, 100] (percentage of user's max HP).
- If `healing` > 0, the move restores HP to the user (not the target).
- Healing is capped at the user's max HP (cannot overheal).

## Type Chart Rules

### TR-1: Type Validity

- All type references MUST be one of the 7 valid types.
- The type chart MUST define effectiveness for all 7 × 7 = 49 type combinations.
- Effectiveness values MUST be one of: 0.0, 0.5, 1.0, 1.25, 2.0.

### TR-2: Type Effectiveness Constraints

- A type MUST NOT be super effective against itself (diagonal = 1.0 or 0.5,
  never 2.0).
- A type MUST NOT be immune to itself (diagonal ≠ 0.0).
- Yang and Yin MUST be super effective against each other (2.0× both
  directions).
- Yang and Yin MUST have neutral (1.0×) effectiveness against all 五行 types.

### TR-3: Five Elements Cycle Compliance

- The generating cycle (相生) defines generating matchups (1.25×).
- The overcoming cycle (相克) defines super effective matchups (2.0×).
- The overcome cycle (被相克) defines not-very-effective matchups (0.5×).
- Each 五行 type MUST be super effective against exactly one other 五行 type
  (相克).
- Each 五行 type MUST generate exactly one other 五行 type (相生, 1.25×).
- Each 五行 type MUST be not very effective against exactly one other 五行 type
  (被相克, 0.5×).
- Each 五行 type MUST be generated by exactly one other 五行 type (1.25× when
  defending).

## Status Effect Rules

### SR-1: Status Identity

- Each status effect MUST have a unique `id`.
- Status `type` MUST be one of: Burn, Poison, Confusion, Chain, Charm.
- Each status type MUST have exactly one definition (no duplicates).

### SR-2: Status Duration

- `duration` MUST be an integer ≥ 0.
- If `duration` is 0, the status is permanent until cured or character switches
  out.
- Maximum duration for any status MUST NOT exceed 10 turns.

### SR-3: Status Damage

- `damagePerTurn` MUST be an integer ≥ 0 (percentage of max HP).
- Burn damage per turn MUST be 6.25% (1/16) of max HP.
- Poison damage escalates: base 1.56% × turns_poisoned, capped at 25%.
- Confusion, Chain, and Charm do NOT have damagePerTurn (value = 0).

### SR-4: Status Stat Modifications

- Burn: Attack ×0.5 (applied as flat multiplier, not stage change).
- Charm: Attack ×0.5 (applied as flat multiplier, not stage change).
- Chain: Speed ×0.5 (applied as flat multiplier, not stage change).
- Poison: No stat modification.
- Confusion: No stat modification.

### SR-5: Status Interaction Rules

- A character can have at most ONE status effect at a time.
- Applying a new status replaces the existing status.
- Status effects are removed when the character switches out or the battle ends.
- Status effects do NOT stack (e.g., two Burns do not double the damage).

## Data Validation Rules

### VR-1: Referential Integrity

- All character move references MUST point to existing move IDs.
- All move type references MUST be valid types.
- All move effect references MUST be valid status types.
- No circular dependencies between data definitions.

### VR-2: Completeness

- All 9+ characters MUST be fully defined (all required fields populated).
- All moves referenced by characters MUST be fully defined.
- The type chart MUST have all 49 entries populated.
- All 5 status effects MUST be fully defined.

### VR-3: Balance

- No character may have all four stats above 300 (prevent overpowered
  characters).
- No move may have power > 200 AND effectChance > 50 AND hitCount > 1 (prevent
  overpowered moves).
- The total number of moves across all characters (counting duplicates) MUST be
  ≥ 12 (ensure variety).
- At least 2 moves per character MUST have `power > 0`.
- **Dual-Type Balance**: No dual-type character may have a defensive matchup
  that results in a 4.0× weakness (both types 相克 by the same attack type) to
  prevent over-punishing.

## File Naming Conventions

### FNR-1: Resource Files

- Character files: `resources/characters/{character_id}.tres`
- Move files: `resources/moves/{move_id}.tres`
- Type chart: `resources/type_chart.gd`
- Status effects: `resources/status_effects.gd`

### FNR-2: Naming Pattern

- All file names MUST be lowercase snake_case.
- Character IDs MUST match their file name (e.g., `zhuge_liang.tres` has
  `id = "zhuge_liang"`).
- Move IDs MUST match their file name (e.g., `fire_strike.tres` has
  `id = "fire_strike"`).
