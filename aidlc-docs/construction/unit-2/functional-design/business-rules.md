# Business Rules — Unit 2: Game Foundation

## Overview

Business rules and validation constraints for the game foundation layer. These
ensure correct state machine behavior, scene transition integrity, save data
consistency, and audio management.

---

## Game State Rules

### GR-1: State Machine Validity

- The GameManager MUST manage exactly 5 states: `TITLE`, `CORPS_CREATION`,
  `CHARACTER_SELECT`, `BATTLE`, `RESULT`.
- State transitions MUST follow the defined loop:
  `TITLE → CORPS_CREATION → CHARACTER_SELECT → BATTLE → RESULT → TITLE`.
- No pause, settings, or game-over sub-states exist in v1.
- The GameManager MUST NOT allow arbitrary state jumps (e.g., `TITLE → BATTLE`
  is invalid).

### GR-2: State Transition Preconditions

- Transition to `CORPS_CREATION` requires no preconditions (entry from
  `TITLE`).
- Transition to `CHARACTER_SELECT` requires:
  - `CorpsRoster.corps_characters` contains exactly 6 unique character IDs.
- Transition to `BATTLE` requires:
  - `CorpsRoster.battle_characters` contains exactly 3 unique character IDs.
  - All `battle_characters` IDs MUST be present in `corps_characters`.
- Transition to `RESULT` requires the battle to have ended (signal from
  BattleManager).
- Transition to `TITLE` from `RESULT` has no preconditions.

### GR-3: State Persistence

- The current game state is NOT persisted to save data (v1 does not support
  mid-game resume).
- On game launch, the state is always `TITLE`.
- The `selected_character` in save data is the last selected character for
  display purposes only, not for state restoration.

## Scene Transition Rules

### SR-1: Transition Exclusivity

- Only ONE scene transition can be active at a time.
- Concurrent transition requests MUST be rejected (log warning, ignore).
- A transition is considered active from initiation until `transition_complete`
  signal is emitted.

### SR-2: Transition Animation

- All scene transitions MUST use the custom transition system (AnimationPlayer +
  CanvasLayer overlay).
- The transition overlay MUST render above all scene content (high z-index
  CanvasLayer).
- Default transition: `FADE_TO_BLACK`, 0.5s duration, 0.1s hold time.
- Transition duration MUST be > 0.0 seconds.
- The fade overlay color defaults to black (0, 0, 0, 1).

### SR-3: Scene Loading Error Handling

- If `change_scene_to_file()` fails (invalid path, corrupted scene), the
  transition MUST:
  - Log an error with the failed path.
  - Keep the transition overlay visible with an error message.
  - NOT crash the game.
- Scene paths MUST be validated as `res://` paths before attempting to load.

## Character Selection Rules

### CSR-1: Corps Selection (CorpsCreation screen)

- Corps selection is handled on the dedicated `CorpsCreation` screen.
- The player MUST select exactly 6 unique characters to form their corps.
- Duplicate selections are NOT allowed (each character can only be in the corps
  once).
- The "Confirm" button MUST be disabled until exactly 6 characters are selected.
- The player can deselect and reselect characters freely before confirmation.
- Once confirmed, the corps is saved to `CorpsRoster.corps_characters` and the
  player proceeds to the `CharacterSelect` screen (Phase 2).
- Saved corps data is persisted and restored on next launch.

### CSR-2: Opponent Corps Generation

- The opponent's corps MUST consist of 6 unique character IDs.
- The opponent's corps is generated by the system when transitioning from
  CorpsCreation to CharacterSelect.
- The opponent's corps MAY overlap with the player's corps (same character on
  both sides is allowed in v1).
- Opponent generation logic is implemented in Unit 4 (AI System).

### CSR-3: Battle Selection (CharacterSelect screen)

- Battle selection is handled on the dedicated `CharacterSelect` screen (Phase 2 only).
- The player MUST select exactly 3 characters from their 6-character corps.
- All 3 selections MUST be from the `corps_characters` list.
- Duplicate selections are NOT allowed.
- Selection order is tracked and determines battle deployment order.
- The "Deploy" button MUST be disabled until exactly 3 characters are selected.
- The player can deselect and reselect freely before deploying.
- The opponent's 6-character corps MUST be displayed as read-only.

### CSR-4: Character Information Display

- During both phases, the following information MUST be visible for each
  character:
  - Character name
  - Character type(s) (primary and secondary if present)
  - All six base stats (HP, Attack, Defense, Speed, Intelligence, Spirit)
  - Character description (flavor text)
  - Move list (4 moves with names and types)
- The opponent's corps in Phase 2 is display-only (no interaction).

## Save Data Rules

### SDR-1: Save File Location and Format

- Save data MUST be stored in a single file: `user://save.cfg`.
- The file format MUST use Godot's ConfigFile (INI-style key-value pairs).
- The file MUST contain three sections: `settings`, `progress`, `meta`.
- No additional save files are created (no `settings.cfg`, `progress.cfg`,
  etc.).

### SDR-2: Save Data Scope

- The save system MUST persist only the following data:
  - Master volume (Float, 0.0–1.0)
  - BGM volume (Float, 0.0–1.0)
  - SFX volume (Float, 0.0–1.0)
  - Master muted state (Bool)
  - Last selected character ID (String)
  - Last battle result (Bool: won/lost)
  - Last battle timestamp (ISO 8601 String)
  - Corps character IDs (JSON-serialized Array[String], 6 IDs)
- The save system MUST NOT store: battle statistics, unlocked characters, play
  time, replay data, character progression, or achievement flags.

### SDR-3: Save Version Handling

- The save file MUST include `meta.save_version` set to `1` (current version).
- On load, if `save_version` is missing or does not match `1`, the save data
  MUST be reset to defaults.
- No migration logic is implemented in v1 (version mismatch = reset).

### SDR-4: Save Error Handling

- If the save file does not exist on load, return default SaveData (first launch
  scenario).
- If the save file is corrupted (parse error), log a warning and return default
  SaveData.
- If a save operation fails (disk full, permissions), log a warning and continue
  (save failure is non-fatal).
- Missing individual keys within a valid file default to their standard values.

### SDR-5: Save Data Security

- No sensitive data (PII, credentials, payment info) is stored in the save file.
- Save data is stored in Godot's user data directory (sandboxed by browser on
  Web).
- Encryption is NOT required (single-player offline game).

## Audio Rules

### AR-1: Audio Bus Hierarchy

- The audio system MUST define three buses: `Master`, `BGM`, `SFX`.
- `BGM` and `SFX` MUST be children of `Master`.
- Volume changes on `Master` affect all audio output.
- Each bus MUST support independent volume control (0.0–1.0 linear scale).

### AR-2: BGM Playback

- BGM tracks MUST loop continuously until replaced or stopped.
- Only ONE BGM track can play at a time.
- BGM playback is scene-driven: each scene specifies its BGM track ID.
- When transitioning between scenes with different BGM, a crossfade MUST be used
  (default 1.0s duration).
- If the same BGM track is requested while already playing, it is a no-op (no
  restart).

### AR-3: SFX Playback

- SFX are one-shot: play once and auto-free on completion.
- Multiple SFX can play simultaneously (polyphony).
- SFX playback does not interrupt BGM.
- SFX tracks MUST NOT loop.

### AR-4: Volume Control and Persistence

- Volume changes MUST be applied immediately via
  `AudioServer.set_bus_volume_db()`.
- Volume values are stored as linear (0.0–1.0) and converted to dB internally.
- All volume changes MUST be persisted to SaveManager immediately.
- Muting the Master bus mutes all audio output.
- Individual bus mute is NOT exposed in v1 (only Master mute).

### AR-5: Dynamic Music Layers

- Dynamic music layers are ONLY active during `BATTLE` state.
- The battle BGM MUST support at least 3 intensity layers:
  - Layer 0: Base melody (always on)
  - Layer 1: Percussion (intensity >= 1)
  - Layer 2: Full ensemble (intensity >= 2)
- Layer transitions MUST use fade in/out (no abrupt cuts).
- Intensity level is provided by BattleManager (Unit 3).

### AR-6: Web Autoplay Policy

- On Web platform, the AudioContext starts suspended (browser autoplay policy).
- AudioController MUST resume audio on the first user input gesture (click,
  keypress, touch).
- Before the first user gesture, BGM MUST NOT attempt to play (silent no-op).
- A "click to start" prompt or similar UX is handled by the Title screen.

### AR-7: Audio Track Registration

- All audio tracks MUST be registered with the AudioController before playback.
- Track IDs MUST be unique within the registry.
- BGM tracks MUST have `loop = true`.
- SFX tracks MUST have `loop = false`.
- Unregistered track ID requests MUST log a warning and be ignored.

## Project Configuration Rules

### PCR-1: Autoload Registration

- The following autoloads MUST be registered in `project.godot`:
  - `DataRegistry` (Unit 1, already registered)
  - `GameManager`
  - `SaveManager`
  - `AudioController`
- Autoload order matters: `DataRegistry` first (data available for others), then
  `SaveManager`, then `AudioController` (depends on SaveManager), then
  `GameManager` (depends on all).

### PCR-2: Display and Window Settings

- Window size: 1280×720 (already configured).
- Stretch mode: `canvas_items` (already configured).
- No additional rendering or physics settings are configured in v1.

### PCR-3: Input Map

- The input map MUST use Godot's default UI actions only: `ui_accept`,
  `ui_cancel`, `ui_up`, `ui_down`, `ui_left`, `ui_right`.
- No custom battle or menu input actions are defined in v1.
- Gamepad support uses Godot's default mappings (no custom configuration).
